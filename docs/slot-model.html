Slots and variants

How a piece of creative work moves through the system: what a slot is, how competing variants relate to each other, and why the winner can be changed without undoing anything.

The shape

A slot is one creative intent — "the hero banner". Inside it, variants are competing candidates for that intent. Inside each variant, a version chain records the fix history: v1 → v2 → v3, strictly linear.

The rule that keeps this readable is that chains never fork. If two people fix the same version two different ways, that is not a branch — it is a second variant. So every arrow downward is time, and every step sideways is an alternative.

Why changing the winner costs nothing

Only one thing about completion is stored: approved_by, on a single image. Everything else — whether the slot is complete, which variants are archived, what the card's headline says — is derived from it on read.

Known gap. Variant selection is under-exposed on the project page: the History tree only renders once a slot already has more than one variant or version, and "Add variant" sits in a hover-only menu.
